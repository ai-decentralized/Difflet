## 2. 根因 1：每个 torchrun 进程试图加载所有 rank

原始行为：

```python
NovaPipeline.from_pretrained(..., start_rank_id=None, local_ranks_size=None)
```

最终进入：

```python
NeuronFluxApplication.load(..., start_rank_id=None, local_ranks_size=None)
```

`NeuronConfig` 默认：

```python
start_rank_id = 0
local_ranks_size = world_size
```

所以 4 个 torchrun 进程里，每个进程都尝试加载 rank `0...3`。但在 PJRT MPMD 模式下，每个 Python 进程只可见一个 NeuronCore，因此会报：

```text
Invalid device index. Device index must be between 0 and 0.
```

### 修复 1：NovaPipeline 自动推断 per-process load range

文件：`nova/pipeline/nova_pipeline.py`

新增：

```python
def _resolve_load_rank_range(start_rank_id, local_ranks_size):
    if start_rank_id is not None or local_ranks_size is not None:
        return start_rank_id, local_ranks_size

    world_size = _env_int("WORLD_SIZE")
    rank = _env_int("RANK")
    if world_size is not None and world_size > 1 and rank is not None:
        return rank, 1

    return None, None
```

行为：

- 单进程：仍沿用 config 默认值
- torchrun 多进程：默认每个进程只加载自己的 global rank
- 显式传 `start_rank_id/local_ranks_size`：保留用户设置

新增单测：

- `test_torchrun_load_defaults_to_one_rank_per_process`
- `test_explicit_load_rank_range_is_preserved`

## 3. 根因 2：ModelBuilder 仍使用旧的 `neuron_config.local_ranks_size`

第一次修复后仍失败。原因是：

```python
NeuronApplicationBase.load_weights(...)
```

虽然拿到了 `start_rank_id/local_ranks_size` 参数，但 `get_builder().shard_checkpoint()` 使用的是 `self.neuron_config.start_rank_id/local_ranks_size`，不是局部变量。

所以只改 `start_rank_tensor` 不够，builder 仍按旧配置 sharding。

### 修复 2：load_weights 写回 neuron_config 并重建 builder

文件：`nova/core/application_base.py`

新增逻辑：

```python
if (
    start_rank_id != self.neuron_config.start_rank_id
    or local_ranks_size != self.neuron_config.local_ranks_size
):
    self.neuron_config.start_rank_id = start_rank_id
    self.neuron_config.local_ranks_size = local_ranks_size
    self._builder = None
```

重新运行后，日志变为：

```text
INFO:Neuron:Sharding weights for ranks: 0...0
INFO:Neuron:Sharding weights for ranks: 1...1
INFO:Neuron:Sharding weights for ranks: 2...2
INFO:Neuron:Sharding weights for ranks: 3...3
```

说明 rank range 修正确实生效。

## 4. 根因 3 尝试：多组件 load 需要 rank lockstep

`NeuronFluxApplication.compile()` 已经因为 race 加过 barrier。load 也有类似风险：快的 rank 可能先进入下一个 component，慢的 rank 还在当前 component 的 NRT 初始化/权重搬运。

### 修复 3：Flux load 每个 component 前后 barrier

文件：`nova/models/flux/application.py`

把：

```python
self.pipe.text_encoder.load(...)
self.pipe.text_encoder_2.load(...)
self.pipe.transformer.load(...)
self.pipe.vae.decoder.load(...)
```

改为：

```python
self._load_component(...)
...

def _load_component(...):
    _spmd_barrier()
    component.load(...)
    _spmd_barrier()
```

这个改动没有解决最终 SIGSEGV，但仍是正确的同步约束，建议保留；否则多组件 load 顺序不稳定。

## 9. 2026-05-08 追加修复：最终可运行协议

后续继续排查后，发现上面的“torchrun per-process load range”方向只解决了早期
invalid-device 的一部分表象，但不是 Flux/NxDI diffusion 的正确运行协议。

### 9.0 详细排障时间线

#### Step A：修掉最早的 invalid device

最初在 `torchrun --nproc_per_node=4` 下运行：

```bash
PATH=/opt/aws_neuronx_venv_pytorch_2_9_nxd_inference/bin:$PATH \
PYTHONPATH=/home/ubuntu/nova \
TORCH_DISABLE_ADDR2LINE=1 \
NEURON_RT_LOG_LEVEL=ERROR \
torchrun --master_port=29514 --nproc_per_node=4 examples/flux_example.py \
  --model black-forest-labs/FLUX.1-dev \
  --tp-degree 4 \
  --skip-warmup \
  --num-inference-steps 1 \
  --prompt "a cat" \
  --output /tmp/flux_rankrange_test.png
```

早期失败点是 `neuron::parallel_load` 的 device index 校验：

```text
Invalid device index. Device index must be between 0 and 0
```

当时观察到每个 torchrun 进程都尝试加载完整 rank range，而单个 PJRT MPMD
进程只看到一个本地 Neuron device。于是先做了两层修复：

- `nova/pipeline/nova_pipeline.py`：如果环境里有 `WORLD_SIZE>1` 和 `RANK`，
  默认传入 `(start_rank_id=RANK, local_ranks_size=1)`。
- `nova/core/application_base.py`：把传入的 rank range 和 builder/runtime 初始化拆开，
  让 `nxd_model.initialize()` 在一进程一 core 时使用本地 device offset 0。

该改动把日志推进到：

```text
Sharding weights for ranks: 0...0
Sharding weights for ranks: 1...1
Sharding weights for ranks: 2...2
Sharding weights for ranks: 3...3
```

invalid-device 消失，但随后进入 SIGSEGV。说明 rank offset 的确是一个问题，
但不是完整问题。

#### Step B：尝试把 CLIP / decoder 作为单核 replicated component

因为 Flux 里 CLIP 和 VAE decoder 本身 `tp_degree=1`，一开始推断它们不应该编译成
`world_size=4`。于是试过：

```python
clip_neuron_config = NeuronConfig(tp_degree=1, world_size=1, torch_dtype=dtype)
decoder_neuron_config = NeuronConfig(tp_degree=1, world_size=1, torch_dtype=dtype)
```

这样做的动机：

- CLIP / decoder 不需要 tensor parallel。
- 如果每个 rank 都本地加载一个单核副本，理论上可避免 DP=4 下的 weight/init 复杂度。
- 可以避免 `tp=1, world=4` 的 component 在 MPMD 下使用跨 rank communicator。

但这个方向马上暴露出 compile race。`--precompile-only` 时多个 torchrun rank 同时看到
`world_size` mismatch，并同时编译同一个 component workdir：

```text
/tmp/nxd_model/text_encoder/
FileNotFoundError in shutil.rmtree(self.compiler_workdir)
```

根因是 `_compile_component()` 之前只用目录存在判断是否已编译，而 `neuron_config.json`
会在 compile 早期写入，导致 rank 间可能把“正在编译中的目录”误判为可用缓存。

因此加了：

- cache hit marker 改成 `model.pt`。
- 额外读取 `neuron_config.json`，比较 `tp_degree/world_size/start_rank_id/local_ranks_size`。
- 对 `world_size=1` component，加 compile owner 逻辑：torchrun 下只有 rank 0 编译，
  其他 rank 等待 artifact。
- 因为 precompile 阶段 torch distributed process group 未必初始化，`barrier()` 不是
  可靠同步点，所以又加了基于 `model.pt` 的轮询等待。

#### Step C：确认旧 artifact 已经被 race 污染

在 world_size=1 实验中，曾经产生过一个表面存在但实际不可用的 CLIP artifact。
验证脚本只加载 CLIP：

```bash
PATH=/opt/aws_neuronx_venv_pytorch_2_9_nxd_inference/bin:$PATH \

随后 rank 0 owner 重新编译 CLIP 后，同样的单组件 load 通过：

```

这一步确认：此前 SIGSEGV 至少有一部分来自 race 产生的坏缓存。

#### Step D：world_size=1 component 方向继续失败

修复坏缓存后，再跑完整 torchrun smoke，CLIP 可以过，但 T5 失败：

```text
RuntimeError: Expected weight tensors for 4 ranks. Recieved 1
```

这个错误说明：

- T5/transformer 的 compiled artifact 是 `world_size=4`。
- TorchScript initialize 需要 4 个 rank 的 weight tensor list。
- 不能把 TP=4 component 的 weight sharding layout 改成每进程只生成 1 rank。

于是 `application_base.load_weights()` 调整为：

- 对 TP>1 compiled artifact，weight list 仍按 compiled layout `0...3` 生成。
- runtime start rank 仍可单独传本地 offset 0。

之后 T5 的 “Expected weight tensors for 4 ranks” 消失，但进入 NRT communicator 错误：

```text
World size of neff 4 is greater than world size of global communicator 1
RuntimeError: Could not load the model status=2 message=Invalid
```

加 `NEURON_RT_NUM_CORES=4` 到 torchrun 命令仍失败，NRT dump 里每个进程仍只形成
world size 1 的 global communicator。这说明 torchrun MPMD 本身和当前 NxDI
diffusion artifact 的 load 方式不匹配。

#### Step E：单进程 4 cores 仍需修 load 顺序

切换到单进程：

```bash
NEURON_RT_NUM_CORES=4 \
/opt/aws_neuronx_venv_pytorch_2_9_nxd_inference/bin/python examples/flux_example.py \
  --model black-forest-labs/FLUX.1-dev \
  --tp-degree 4 \
  --skip-warmup \
  --num-inference-steps 1 \
  --prompt "a cat" \
  --output /tmp/flux_singleproc_test.png
```

如果按原始顺序先加载 CLIP，后加载 T5，会失败：

```text
Loading Flux component .../text_encoder/
world size to 1
...
Loading Flux component .../text_encoder_2/
World size of neff 4 is greater than world size of global communicator 1
```

推断：第一个 Neuron component 会建立当前进程的 runtime collective communicator。
如果第一个加载的是 `world_size=1` component，后续 TP=4 component 无法扩大 communicator。

所以 load 顺序改成：

```text
text_encoder_2 -> transformer -> text_encoder -> decoder
```

这使 T5 和 transformer load 成功，但当 CLIP/decoder 仍是 `world_size=1` 时，完整进程中
再加载 CLIP 会 SIGSEGV。由此推翻了 “CLIP/decoder 用 world_size=1 replicated”
这个方向：当前 NRT 进程内不能稳定混用 `world_size=4` 和 `world_size=1` traced model。

#### Step F：最终方案：所有 Flux Neuron component 保持 world_size=4

最终把 CLIP 和 decoder 改回：

```python
clip_neuron_config = NeuronConfig(tp_degree=1, world_size=world_size, torch_dtype=dtype)
decoder_neuron_config = NeuronConfig(tp_degree=1, world_size=world_size, torch_dtype=dtype)
```

这代表：

- CLIP/decoder 仍是 `tp_degree=1`。
- 但它们作为 Flux pipeline 的 Neuron component，runtime world 与 T5/transformer 一致。
- 对 CLIP/decoder 来说这是 DP=4-style artifact；对 runtime 来说 communicator 始终是 4。

强制重编后，单进程 4 cores 完整 smoke 通过。

### 9.1 关键新发现

1. **torchrun MPMD 不适合当前 TP=4 Flux artifact 的 load**
   - `torchrun --nproc_per_node=4` 下每个进程看到的 Neuron communicator 仍会在
     TP=4 component load 时表现为 world size 1。
   - 典型错误：

```text
World size of neff 4 is greater than world size of global communicator 1
RuntimeError: Could not load the model status=2 message=Invalid
```

2. **不能混用 world_size=4 和 world_size=1 component**
   - 把 CLIP/VAE decoder 改成 `world_size=1` 后，单独 CLIP 可 load。
   - 但完整 pipeline 中先 load TP=4 的 T5/transformer，再 load world_size=1 的
     CLIP，会在 CLIP initialize 原生层 SIGSEGV。
   - 结论：当前 NRT 进程内应保持 Flux 四个 Neuron component 的
     `neuron_config.world_size` 一致。

3. **load 顺序有硬约束**
   - 先 load world_size=1 CLIP 会把 communicator 初始化成 1，后续 TP=4 T5 失败。
   - 正确顺序是先 load 全局 TP component：
     `text_encoder_2 -> transformer -> text_encoder -> decoder`。

### 9.2 最终代码调整

- `nova/models/flux/application.py`
  - CLIP 和 VAE decoder 改回 `world_size=world_size`，保持四个 component 的
    runtime world 一致。
  - load 顺序改为先 T5、transformer，再 CLIP、decoder。
  - `_compile_component()` 保留 component config mismatch 检查，避免旧缓存静默复用。
  - 对 replicated/single-world component 的 compile owner/wait 逻辑保留，但当前
    Flux 默认不再走 `world_size=1`。
- `nova/core/application_base.py`
  - 对 TP>1 traced artifact，不再把 torchrun per-process `(rank, 1)` 写入
    `neuron_config` 作为 weight sharding layout。
  - weight list 仍按 compiled layout `0...world_size-1` 生成；runtime local offset
    仍可单独映射。

- `--skip-warmup` 只跳过 post-load warmup，不影响真实 `pipe(...)` forward；本次
  `num_inference_steps=1` forward 已实际执行并保存图片。

当前结论：M1.4 Flux real smoke 的修复路径是废弃 torchrun MPMD 作为默认运行方式，
改用单进程多 core runtime；Flux component 必须保持一致 world size，并且先加载
TP=4 component 初始化 communicator。

### 9.5 本轮文件变更与实验索引

代码/文档变更：

- `nova/models/flux/application.py`
  - component cache hit 从目录存在改为 `model.pt + neuron_config.json` 双检查。
  - 增加 `_compiled_config_matches()`，rank layout 改变时自动重编 component。
  - 增加 compile owner / artifact wait 辅助逻辑，避免 torchrun 下多个 rank 同时编译
    同一个 replicated component workdir。
  - 最终保留 CLIP/decoder `world_size=world_size`，不再默认使用 `world_size=1`。
  - load 顺序固定为 `text_encoder_2 -> transformer -> text_encoder -> decoder`。
- `nova/core/application_base.py`
  - 增加 runtime start-rank offset 计算。
  - 避免 TP>1 compiled artifact 在 torchrun 实验中被错误改成只生成 1 rank weight list。
  - 增加 initialize 前后的 rank logging。
- `nova/pipeline/nova_pipeline.py`
  - 保留 torchrun env 下自动推断 `(RANK, 1)` 的逻辑，主要作为后续 MPMD 实验基础。
- `tests/unit/test_pipeline.py`
  - 增加 torchrun rank range 推断和显式 rank range 保留的单测。
- `examples/flux_example.py`
  - 增加 `--skip-warmup`。
  - 顶部使用说明改为 `NEURON_RT_NUM_CORES=N python ...`，并标注当前不要用 torchrun。
- `nova/pipeline/compile_cache.py`
  - manifest schema bump 到 2，用于使旧缓存进入组件级一致性检查。

这些改动中有几个看起来像中间产物，但建议保留：

- `_compiled_config_matches()` 必须保留。Flux component artifact 不是只由顶层 cache key
  决定，component 内部 `neuron_config.world_size/local_ranks_size` 改动也会影响能否 load。
  没有这个检查，`model.pt` 存在但 rank layout 不一致时会静默复用旧 artifact。
- `model.pt` marker 检查必须保留。只检查目录存在会把正在编译中的目录当成完成缓存，
  这是最早空 cache / 坏 artifact 的来源之一。
- compile owner / wait 逻辑目前不是默认成功路径必需，因为最终 Flux 不再默认使用
  `world_size=1` component；但它能保护未来如果再次引入 replicated component 时不重犯
  多 rank 同目录编译 race。
- `compile_cache.py` schema version bump 必须保留。否则已经生成过的旧 manifest 会让
  `NovaPipeline.from_pretrained()` 顶层直接 cache hit，根本进不到 component 级
  config mismatch 检查。
- `examples/flux_example.py` 的 `--skip-warmup` 不是修复本身，但它是硬件 smoke 必要的
  调试开关；可以把 load 和 forward 的问题分开定位。
