Difflet on AWS Trainium2 · trn2.3xlarge · TP4

How fast do the weights get onto the chip?

Difflet runs the same diffusion models on two backends: PyTorch-native (“native”) and ahead-of-time compiled (“AoT”). Before a model can draw anything, billions of numbers have to travel from disk to the accelerator. This page explains how each backend does that, which one is faster for each of our four models, and why.

Cold start · weights come from disk

Whoever reads fewer bytes wins.

Native is faster for HunyuanVideo and LTX-2, level with AoT for Qwen-Image, and slower for Wan2.1. The disk is the bottleneck, so the amount each side reads most likely decides it. cause inferred

Warm start · weights are already in memory

About even, often slightly in AoT’s favour.

Native copies its share of the weights faster (3.6–5.4 s vs 12–28 s for the main model), but it also builds the model and runs a warm-up pass. Counted until the model is ready, AoT is 1–5 s ahead for three of the four models.

Whole request · warm

Weights are not where native loses time.

Native spends 9–27 s starting its processes before loading even begins, and in the benchmarked setup ran slower video decoders. Those, not weight loading, explain why its warm requests take longer.

01 · Vocabulary

Six words you need

Weights
The numbers a trained model has learned. A 13-billion-parameter model is 13 billion of them. Running the model means multiplying your input by these numbers, so they must sit next to the accelerator.
Checkpoint
The files on disk that hold the weights, as published by the model’s authors (here in Hugging Face’s safetensors format).
bf16 and fp32
Two ways to store each number: bf16 takes 2 bytes, fp32 takes 4. Both backends run most components in bf16 (a few stay in fp32), so an fp32 checkpoint means reading twice the bytes that end up being used.
NeuronCore and HBM
The accelerator has 4 NeuronCores. Each has 24 GiB of its own fast memory (HBM). Weights must end up in HBM before a core can use them.
TP4
“Tensor parallel across 4 cores”: each large layer is cut into 4 slices, one per core, so a model too big for one core fits on four. Every run on this page uses TP4.
Page cache
Linux keeps a copy of recently read files in spare RAM. Reading a file the second time comes from RAM, not disk. This is what makes a “warm” start warm.

02 · Anatomy

What is inside each model

All four models follow the same recipe. A text encoder turns the prompt into numbers, the DiT (diffusion transformer) turns random noise into a picture or video over many steps, and a VAE decoder expands the result to full size. The DiT is by far the largest part, and it runs 50 times (or 100) per request while the others run once.

03 · One request, start to finish

Where loading fits

Each difflet generate runs these steps in order. Loading is step 2, and it happens on every request unless a server keeps the model resident.

  1. Launch. Start the processes and connect them to the cores.
  2. Load weights. Move every component’s weights to where it runs.
  3. Warm up. Run the model once on dummy input. This traces the model and loads its compiled programs (native only; AoT prepared everything at compile time).
  4. Encode the prompt with the text encoder(s).
  5. Denoise: run the DiT 50 times.
  6. Decode the latent with the VAE and write the file.

04 · Two strategies

Cut the weights when you load, or cut them ahead of time

With TP4 every big layer has to be cut into four slices. The two backends differ mainly in when that cutting happens and who does the reading.

Native: cut at load time

core 0core 1core 2core 3
  1. One process per core starts. Each builds an empty outline of the model that takes no memory.
  2. It checks that its share fits in its core’s 24 GiB before reading anything.
  3. It opens the original checkpoint and reads only its own quarter of each split layer (small shared pieces are read whole), one tensor at a time, converting to bf16 on the way.
  4. Weight store: the first time, if a ready-cut copy would be at least 10% smaller than what it just read, it saves one. That only happens for fp32 checkpoints loaded as bf16 (in practice the Wan2.1 DiT and LTX-2’s Gemma-3). Later loads read that copy instead.
  5. It runs one warm-up pass, which traces the model and loads its compiled programs.
  6. Text encoders that run on the host CPU are loaded whole, by the first process only, with the standard Hugging Face loader.

AoT: cut once, at compile time

compile
whole checkpoint → 4 pre-cut bf16 files
read by
one process

core 0core 1core 2core 3
  1. At compile time, one process reads the whole checkpoint into RAM, converts it to bf16 and writes one file per core (2 to 21 minutes in our runs: Wan2.1 119 s, HunyuanVideo 313 s, Qwen-Image 362 s, LTX-2 391–1269 s). The files are shared and reused when you compile another resolution.
  2. At start-up, one process per stage (text encoder, DiT, VAE) reads all four files for that stage.
  3. It hands each core its file in one step. The compiled program was built with the model, so no warm-up pass is needed.

05 · Cold and warm

Why the first run is so much slower

The disk on this machine reads about 130 MB per second. At that speed every gigabyte costs about 7.7 seconds, so the 25.6 GB HunyuanVideo DiT alone takes over three minutes to read. Copying the same bytes from RAM takes seconds.

Cold start means the weights are not in RAM: the machine just booted, or other files pushed them out of the page cache. The disk is the bottleneck, and the backend that reads fewer bytes wins.

Warm start means the files were read recently and Linux still has them in the page cache. Disk speed no longer matters. What remains is copying into HBM plus each backend’s fixed start-up work.

The benchmarks force a cold start by telling Linux to drop its page cache before the run.

07 · What native can improve

Where native weight loading can get faster

These are proposals. None of them has been measured yet; the expected effect is estimated from the numbers above.

Use the disk while the processes are still starting

On a cold start, native spends 9–27 s launching its processes and building the model outline before the first byte of weights is read, and the disk sits idle meanwhile. Starting to read the weight files into the page cache as soon as the command runs, before the processes are up, puts that idle time to use.

Expected: up to ~20 s off a cold start. (Reading the text encoder and the DiT at the same time would not help on this machine: the reads already run at the disk’s full speed, ~130 MB/s, one after the other.)

Load umT5 in bf16, if accuracy allows

Wan2.1 most likely loses its cold-start race because umT5 stays in fp32, so the weight store never applies and 22.7 GB are re-read every time. If a bf16 umT5 passes an accuracy check (the code notes it is sensitive to bf16), the store would hold an 11.4 GB copy.

Expected: about 85 s off Wan2.1’s cold start, roughly closing the gap to AoT. Needs an accuracy check first.

Write the weight store off the critical path

The store is written during the first load. On 2026-10-19 that write took Wan2.1’s first compile from 314 s to 519 s and LTX-2’s from 119 s to 307 s; in the latest Wan2.1 compile it took 192–215 s per core. It also pushes the just-read checkpoint out of the page cache. Writing after warm-up, in the background, or with a hint to Linux not to cache the written pages would remove both costs.

Expected: about 3 minutes off the first compile for Wan2.1 and LTX-2.

Shrink the fixed cost of every request

Every native request pays the process launch (9–27 s) and a warm-up pass. The NKI trace cache already cut HunyuanVideo’s warm-up from 36.5 s to 13.5 s. Making the launch time steadier, caching more of the warm-up, and keeping a resident server process so weights load once rather than per request attack the rest.

Expected: 10–20 s per warm request; a resident server removes loading from requests entirely.

Put the weight store on faster storage

On this ~130 MB/s disk, a ready-cut copy only helps when it is smaller than the original, which is why bf16 checkpoints get none. On local NVMe the store would help every model, including bf16 ones, because reading would be several times faster. This has not been tested.

Expected: cold loads limited by NVMe speed instead of the network disk.

Setup. AWS trn2.3xlarge: one Trainium2 device with 4 NeuronCores (24 GiB HBM each), 12 vCPUs, 124.8 GiB RAM, one EBS volume at ~130 MB/s. Every run uses TP4, seed 42 and the prompt “a cinematic shot of a red fox running through a snowy forest”.
