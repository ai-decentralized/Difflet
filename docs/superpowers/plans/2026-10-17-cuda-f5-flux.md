# CUDA F5 — Flux on CUDA (neutral modeling split + tp=1 port) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run FLUX.1-dev on one RTX PRO 6000 at `tp=1` through Difflet's own Flux DiT (`NeuronFluxTransformer2DModel`, built on `difflet.ops`), proven against upstream diffusers with the same three-gate DiT parity and the whole-pipeline e2e oracle Qwen-Image has, without changing what Trainium runs.

**Architecture:** `modeling_flux.py` becomes backend-neutral: the layer-boundary markers come from a backend-resolved `difflet/layers/markers.py` (Trainium's real wrappers there, identity everywhere else), and the three Trainium wrapper classes at the end of the file move to `difflet/models/flux/trainium_backbone.py`. A neutral `FluxDiTConfig` replaces `InferenceConfig` for non-Trainium backends while keeping the attribute names the modeling reads (`config.neuron_config.torch_dtype` / `.world_size`). On CUDA, `CudaFluxTransformerApplication` builds the neutral DiT on the meta device, loads the diffusers safetensors through the existing HF→Difflet key conversion, and a thin `FluxDiTAdapter` gives it diffusers' transformer call signature (`img_ids`/`txt_ids` → rope) so diffusers' own `FluxPipeline` drives CLIP, T5, the DiT, the scheduler and the VAE on one GPU (D8). CLI, registry, parity and e2e follow the Qwen-Image F3/F4 shape exactly.

**Tech Stack:** torch 2.11.0+cu128 eager (D4), SDPA (D7), bf16 (D9), diffusers 0.38.0 (`FluxPipeline`, `FluxTransformer2DModel` as the oracle), pytest, black 100.

**Spec:** `docs/plans/2026-10-16-cuda-backend-support.md` — follow-up **F5 — Flux** ("Split `modeling_flux.py` into neutral modeling + Trainium wrapper; `scripts/flux_smoke.sh` before and after, same cosine; then port with the Phase 4 recipe"), decisions D3, D8, D11, D13, D14; Phase 4 (tasks 4.1–4.5) is the recipe; the F3/F4 status-log entries and `docs/superpowers/plans/2026-10-17-cuda-f4-performance.md` are the worked examples.

## Review Focus

1. The single-block `proj_out` split (`[:, :inner_dim]` → `proj_out_attn`, `[:, inner_dim:]` → `proj_out_mlp`) must use `inner_dim = heads × head_dim`, not the MLP width — Task 2 `test_convert_flux_hf_state_dict_splits_proj_out_at_inner_dim` uses a tiny config whose `mlp_hidden_dim ≠ inner_dim` so a wrong slice fails.
2. `FluxDiTAdapter` must accept `guidance=None` (schnell) and a float/tensor (dev) and feed the DiT a tensor of the model dtype in both cases — Task 3 `test_adapter_handles_guidance_none_and_tensor`.
3. `FluxPipeline` reads `transformer.config.in_channels` (64 → 16 latent channels), `transformer.config.guidance_embeds`, `transformer.dtype`, and may enter `transformer.cache_context(...)` — Task 3 `test_adapter_exposes_what_flux_pipeline_reads`.
4. Rope dtype: the Trainium wrapper casts the stacked `(S, head_dim, 2)` rope to the model dtype; diffusers keeps fp32 cos/sin — the CPU oracle runs fp32 so this is invisible there; the GPU parity gate (Task 3) is the check, and the ledger records the measured cosine.
5. Trainium importers: every consumer of the three moved classes (application, serving orchestrator strings, tests, scripts) must import from `trainium_backbone`; Task 2 Step 3 lists them from `grep -rn` and `tests/unit/models/flux/test_flux_entry.py::test_create_flux_application_wires_config_flow` stays green under the Neuron gate.
