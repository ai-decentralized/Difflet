# CUDA F2 — Second card: data-parallel replicas and CFG-parallel Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Use a second RTX PRO 6000 the way decision D6 orders it: `difflet run --dp 2` runs two single-GPU replicas over a `--requests` batch, and `difflet run --model-id Wan-AI/Wan2.2-T2V-A14B-Diffusers --cfg-parallel` runs the cond and uncond passes on two GPUs under `torchrun` with NCCL — each proven against the single-GPU results (same seeds, same images/videos) with a timing table. Tensor parallel across PCIe stays F6; context parallel stays F2b.

**Architecture:** One process per GPU under `torchrun` (D5). `CudaBackend.prepare_runtime` initialises `torch.distributed` (NCCL, from `ops_impl/platform.py::distributed_backend_name`) when `WORLD_SIZE > 1` and pins `LOCAL_RANK`'s device; `ops_impl/parallel_mesh.init_parallel_mesh` builds one `torch.distributed.new_group` per non-trivial mesh axis from `MeshSpec.axis_groups` (exactly the Trainium recipe) and `get_cfg_group()` / `get_cp_group()` return that group object at world size > 1 (the replica list at world size 1, as today); the CUDA collectives gain the group-aware `all_gather` / `all_reduce` the Wan modeling already calls (`gather_from_tensor_model_parallel_region_with_dim`, `reduce_from_tensor_model_parallel_region`); every scatter is already a local narrow. The Wan modeling's CFG-parallel path (`scatter_to_process_group_spmd` by `get_cfg_rank_spmd(SPMDRank.get_rank())`, gather at the end) then works unchanged on CUDA because `SPMDRank.get_rank()` reads `RANK`. The CUDA CLI re-execs itself under `torchrun --nproc_per_node=<cfg×cp×tp>` when the parallel config needs more than one process and `WORLD_SIZE` is unset (`difflet/cli/runner.py::run_torchrun`), every rank runs the same SPMD generate (the orchestrator loop is deterministic on both), rank 0 writes the output. Data parallel reuses the existing `difflet/cli/dp` router (claims, manifests, schedules) with a CUDA `worker_env` (`CUDA_VISIBLE_DEVICES` per replica, no Neuron variables) and a batch-mode loop in `CudaOneProcessOrchestrator.generate()` (load once, claim requests, generate each, mark done/failed).

**Tech Stack:** torch 2.11.0+cu128 (`torch.distributed`, NCCL, `torch.distributed.run`), gloo for the CPU multi-rank tests (`torch.multiprocessing.spawn`, 2 processes, CPU tensors), diffusers 0.38.0, pytest, black 100.

**Spec:** `docs/plans/2026-10-16-cuda-backend-support.md` — follow-up **F2** ("`torchrun --nproc_per_node=2`; NCCL process groups from `MeshSpec.axis_groups()`; collectives on `torch.distributed`; CFG-parallel for Wan; `ulysses_attention` if a workload needs CP. TP across PCIe is not part of F2."), decisions D5 (one process per GPU under torchrun; Release 1 initialises no `torch.distributed`), D6 (DP and CFG-parallel first), D11 (generic torch-accelerator backend; NCCL name only in `platform.py`), D14 (parity gates). The Trainium mesh (`difflet/backends/trainium/core/parallel_mesh.py`) is the recipe for the groups; `difflet/cli/dp/` is the router to reuse; the F1/F1b plans are the worked examples of the method.

## Rulings

- R1: `get_cfg_group()` returns a `torch.distributed` group object at world size > 1 and the replica list at world size 1; the collectives accept both. Nothing outside the CUDA backend sees the difference.
- R2: both ranks run the whole orchestrator loop (UMT5 encode, scheduler, VAE decode) — SPMD, as on Trainium; only rank 0 writes files. Rank-local memory is therefore the full single-GPU footprint plus nothing.
- R3: CP (`--cp-degree > 1`, `ulysses_attention`) is F2b — the spec makes it need-triggered; `--dp` combined with `--cfg-parallel` is allowed by construction and recorded as unverified.
- R4: multi-rank CPU tests use gloo spawn (2 processes) against the CUDA modules, which import only torch; they are the regression net for the group plumbing without a GPU.
