# CUDA F1 — Wan 2.2 (T2V-A14B) on CUDA at tp=1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Generate a prompt-faithful Wan 2.2 T2V-A14B video on one RTX PRO 6000 at `tp=1` through Difflet's own Wan DiT (`difflet/models/wan/modeling_wan.py`, already backend-neutral) with **both experts resident** and the true-CFG path, proven against upstream diffusers with the same three-gate DiT parity (per expert) and a whole-pipeline e2e oracle, without changing Trainium or TPU.

**Architecture:** The TPU Wan port is the template and most of it is already neutral: `TpuWanConfig`'s geometry (latent frames/height/width, `image_seq_len`, validation) and the checkpoint key rewrite (`ffn.net_in/net_out` ↔ `ffn.net.0.proj/net.2`) are lifted into neutral modules the TPU classes keep subclassing/re-exporting. `CudaWanTransformerApplication` (one expert, `CudaApplicationBase`) builds the neutral `WanTransformer3DModel` on meta and loads the diffusers safetensors through the shared `_torch_megatron` loader with that rename. `CudaWanApplication` mirrors `TpuWanApplication`'s outward contract but keeps everything on the GPU: UMT5 (`transformers.UMT5EncoderModel`, bf16) behind a `(input_ids, attention_mask) → embeds` callable, both experts behind a device-moving callable (the orchestrator holds the loop latents on the host in fp32 — UniPC's corrector collapses in bf16 — so the callable moves per call, as the TPU wrapper does; keeping latents on the device is an F4b-style measured option), diffusers' `AutoencoderKLWan` behind a decoder callable with `.config`, all driven by the backend-neutral `WanOrchestrator` (`difflet/models/wan/pipeline.py`: boundary-ratio expert switch, cond + uncond passes when `guidance_scale > 1`). Entry/registry/CLI/oracles follow F5's shape exactly.

**Tech Stack:** torch 2.11.0+cu128 eager (D4), SDPA (D7), bf16 (D9), diffusers 0.38.0 (`WanPipeline`, `WanTransformer3DModel`, `AutoencoderKLWan`), transformers (UMT5), pytest, black 100.

## Review Focus

1. The checkpoint rename must map every `ffn.net_in` / `ffn.net_out` parameter and nothing else; a strict load on a tiny diffusers `WanTransformer3DModel` checkpoint must succeed for both experts — Task 2 `test_cuda_wan_expert_loads_diffusers_weights_and_matches`.
2. Expert selection by boundary: timesteps ≥ `boundary_ratio × 1000` go to `transformer`, below to `transformer_2`; with `enable_transformer_2=False` the high-noise expert runs every step — Task 3 `test_generate_routes_steps_to_the_boundary_expert` (spy on the two callables with a 4-step run).
3. CFG: `guidance_scale > 1` runs cond and uncond passes per step and combines `uncond + scale × (cond − uncond)`; `guidance_scale_2` applies below the boundary — Task 3 `test_generate_runs_cond_and_uncond_passes` (spy counts: 2 per step), `test_guidance_scale_2_is_used_below_the_boundary`.
4. The UMT5 callable zero-pads past the attention mask and returns `(B, text_seq_len, 4096)` in the model dtype; the orchestrator's `encode_prompt` expects exactly that — Task 3 `test_text_encoder_callable_pads_to_text_seq_len`.
5. The VAE decoder callable must expose `latents_mean` / `latents_std` through `.config` so `_decode_latents` denormalises as diffusers does; decoded frames must be in `[0, 1]` for the e2e metric — Task 3 `test_vae_decoder_callable_exposes_config_and_decodes`, Task 4 e2e script asserts the range.
