0 · 这份文档是什么

项目里已经有一份提案与验证台账文档，它的纪律是每一条主张都必须有实验支撑。这份是它的姊妹篇，性质完全不同：这里记的是还没有被验证的候选方向，以及我对每一条做的可行性核查和反驳尝试。两份分开，是为了不让未验证的构想稀释掉台账的可信度。

它的用途有三个：一是决定接下来做什么；二是防止已经想清楚的死路被反复重提；三是论文写作时，"你为什么不做某某"这类问题在这里能直接找到带数字的回答。

这批想法是怎么来的 从六个互不相同的角度并行生成：片上测量与常驻状态、编译期特化、内存层级与数据流、数值精度作为动作、消灭现存的手调参数、运行时控制平面。每个角度产出三个想法，共 18 个。之后由我逐条查代码做对抗性验证——默认立场是杀死它，只有认真尝试反驳之后仍然站得住的才判存活。

1 · 术语速查

下面这些词在正文里反复出现。先在这里讲清楚，正文就不再打断。

1.1 关于缓存机制本身

词意思
去噪步生成一张图要走 50 步，每一步都让大模型算一次"这一步该往哪个方向走"。这个方向量在文档里记作 v。
锚点步真的让模型算的那些步。当前方案 50 步里只有 12 步是锚点。
被跳步不让模型算、用之前锚点的输出猜一个值顶替的那些步。剩下 38 步都是。
组合系数猜的方式是"最近两个锚点输出的加权和"，那两个权重就是组合系数。整套方案一共 74 个这样的小数，冻结在一个 JSON 文件里。注意它和模型自身的百亿参数完全无关，模型一个字节都没改过。

1.2 关于那套数学（Gram 框架）

内积：两个张量逐元素相乘再全部加起来，得到一个数。它衡量"两个方向有多像、有多长"。关键性质是：它把一个 262144 个元素、512KB 大的张量，压缩成 4 个字节。

Gij = ⟨vi, vj⟩　　（Gram 矩阵，49 × 49 的小表）
符号意思
vi第 i 步模型输出的方向量
⟨·,·⟩内积
Gij第 i 步方向和第 j 步方向的内积；对角线上的 Gii 是第 i 步方向的长度平方
为什么这张小表是整套方法的地基 每个 v 是几百万维的巨型张量，但"用几个方向的组合去逼近另一个方向，误差有多大"这件事，纯粹取决于这些方向两两之间的长度和夹角——也就是这张 49×49 的小表。所以昂贵的高维问题被压缩成了查表运算：最优组合系数是解一个二元一次方程组，剩余误差是一个查表算出的数。整个框架只依赖内积，不依赖别的任何东西——这句话是后面所有想法的出发点。

Schur 补（不必记名字，记含义）：用最优系数组合之后，无论如何都消不掉的那部分剩余误差。直觉是"目标的总能量 − 能被已有方向解释掉的能量 = 解释不了的能量"。它在调度里当作"跳过这一步要付出的质量代价"。

正交化：把一组方向依次调整成互相垂直的等价表示，是数值上更稳的做法。它产生的"残差长度"在数学上恰好等于上面那个 Schur 补。

1.3 关于硬件与编译

词意思
提前编译Trainium 的执行方式：整个模型的一步计算被提前编译成一个固定的大程序（文件叫 NEFF），运行时只能整个执行，不能临时跳过程序内部的某一段。这与显卡上"逐个算子临时调度、想跳哪跳哪"完全不同，是本项目所有硬件约束的总源头。
图就是上面说的那个编译好的大程序。"多个图共存"指显存里同时驻留多个这样的程序。
张量并行把一个大矩阵横着或竖着切开，分给 4 个计算核各算一块，最后再合并。本项目的并行度是 4。
分片被切开之后每个核持有的那一块。
集合通信4 个核合并各自结果的动作。求和式的合并叫全归约（all-reduce），拼接式的叫全收集（all-gather）。每个注意力层和前馈层后面都有一次，一步里上百次。

显存设备上的大内存，96GB。模型权重常驻在这里。
脉动阵列芯片里专门做矩阵乘法的那块硬件，是算力的主体。
别名机制编译图的一个能力：让某个输出原地写回一个常驻的设备变量，从而在多次调用之间保持状态。项目里现有的探针就用它维护一个常驻参数，每次只把几个字节的标量传回主机。difflet/backends/trainium/flux/teacache_probe_fused.py:119
编译缓存键一串哈希值，决定"这份编译产物能不能被复用"。它由模型标识、并行配置、数据类型、图像尺寸、工具链版本等拼出来。任何进入这个键的东西一改，就要重编译 23GB。

1.4 关于实验记录里的运行时词汇

实验记录密集使用下面这些词。它们描述的是"程序怎么被调用、张量住在哪里"，与前面几组是不同的层次。

词意思
入口点一个编译产物里可以被单独调用的程序。同一个产物可以有多个入口点，各自有固定的输入形状。
调度 / dispatch主机让设备执行某个入口点这个动作本身。它有固定开销（这里实测约 337 微秒），与要算的东西多小无关——这是这批实验里反复起决定作用的量。
别名状态用别名机制常驻显存、可以被原地改写的张量（这里是 anchor 与潜变量），多次调用之间保留。
设备侧句柄指向已经在设备上、按核分好的张量的引用。用它把大张量从一个图直接交给另一个图，不经过主机。
落地 / materialize把张量真正读回主机内存，或强制它以某个数据类型在设备上成型。前者是流量成本，后者是数值语义——H1f 失败的正是后者。
staging请求开始时把整个请求都不变的张量一次性写上设备，之后所有步骤复用同一份。
槽位一个活跃请求独占的设备缓冲区，必须在请求结束前不被别人复用，否则会串数据。
判据 / gate实验开始前就冻结下来的通过条件。先写死条件再跑，跑完不许改——防止事后调整及格线。
逐 bit 相同两条路径的输出在每一个数上完全一致（不是"接近"）。用它保证两边跑的确实是同一个算法，这样时间差异才能归因于架构。
HLO编译器的中间表示。"屏障进了 HLO 却被删掉"说的就是它——我们写的意图进了中间表示，却没能活到最终产物。
循环携带状态循环结构里跨轮次传递的状态。用它可以让一次调用跑多轮，从而减少调度次数。
每核执行时间某个入口点在单个计算核上的执行时间。四个核会重叠，所以它只作诊断，不能直接相加。

1.5 关于调度与认证

词意思
动态规划一种能在"哪些步当锚点"的天文数字种组合里，精确找出最优解的算法（不是近似、不是搜索）。前提是代价要能沿步累加。

2 · 设计目标：AOT 硬件约束如何改变 cache abstraction

现有 cache 算法已经有一套成熟的 offline 数学：从完整轨迹恢复 velocity，利用 Gram / 闭式回归求 predictor 系数，再用动态规划选择 anchor。真正需要重做的不是这套数学本身，而是它在 Trainium 上的执行边界。

2.1 保留的算法层

  1. Offline calibration：完整轨迹提供 skipped-step ground truth；Gram 是线性 predictor 误差的充分统计量。
  2. 闭式 predictor：组合系数由校准数据直接求解，不训练模型，也不修改 FLUX 参数。
  3. 静态 schedule / DP：给定质量代价后，anchor 位置仍可由精确动态规划得到。
  4. 策略与模型参数分离：cache policy 是小型元数据，而不是模型权重的一部分。

2.2 Trainium 带来的系统问题

  1. AOT 图固定：运行时不能像 GPU 一样任意在大图内部插分支；频繁改变图结构会触发重新编译。
  2. TP4 数据天然分片：anchor state、predictor 和 telemetry 放在 collective 前还是后，会直接改变 HBM 占用、冗余计算和通信。
  3. 跨 step 的 tensor state 有生命周期：cache 必须保留过去的 anchor output。问题不是“能不能存”，而是应该存在哪里、以什么分片形式存、什么时候 materialize 完整张量。
  4. host/device 边界应当重新定义：大 tensor 数据面应尽量留在 accelerator；主机侧最好只传 coefficient、step id、budget 等标量控制状态。
  5. serving 调度的资源单位是完整 DiT step：一个 anchor 大约对应固定的 accelerator 时隙，因此 cache schedule 可以进一步暴露为 serving scheduler 的资源分配问题。
本文的主设计原则 Large tensor data plane stays on the accelerator; the host operates a scalar control plane.

Offline 数学决定“怎么算”和“默认在哪里算”；Trainium co-design 决定“tensor state 放哪里、predictor 在哪里执行、collective 何时发生、host 到底需要看到什么”。Gram telemetry 只是这条 scalar control plane 上的一个可选观测原语，不再作为论文主问题本身。

3 · 架构主线与它们的实验证据

这里把候选方向按系统层次重新组织。主线先回答一个 architecture 问题：在 AOT tensor accelerator 上，cache state、prediction、communication 和 control 应该如何放置？ Online Gram 只作为 telemetry extension，不再承担整篇工作的中心叙事。

下面每一条主线，都紧跟着检验它的实验：已经跑完的给出记录与判定，还没跑的说明要回答什么、为什么这样设计、以及意义。

主线 AAccelerator-resident request state机制/流量通过；速度拒绝

问题

线性 cache predictor 反复使用过去的 anchor output；denoise loop 反复使用当前 latent、encoder hidden states、pooled projection、guidance 和 rotary embedding。GPU 风格实现容易把这些 tensor 都当作普通 runtime 对象；在 AOT accelerator 上，若它们每次 invocation 都从 host 重传，控制图省下的算力会被数据生命周期吞掉。

设计

按生命周期拆分：模型权重是 model-lifetime；prompt conditioning、anchor ring 和 latent 是 request-lifetime；coefficient、timestep、Δσ 与 action 是 step-lifetime。可变 anchor/latent 用 alias state 原地更新；请求内不变的 conditioning 在初始化时一次 staging 为 ranked device handles；逐 step 的 host 接口只保留标量。H1d 进一步证明 ranked output buffer 本身不是 request identity：host 必须给每个 live request 分配一个在 release 前不复用的 device slot。

研究问题

request state 应保存完整 tensor 还是 TP shard？mutable alias 与 immutable slot 应如何共同管理生命周期？K、context size、slot pool 容量增加时 HBM footprint、admission control 和隔离如何变化？现有证据只证明跨调用常驻 HBM，不应误写成跨调用常驻 scratchpad。

主线 A 的结论：一条可量化的调度地板定律 这条链上真正的对立不是"常驻还是主机"，而是数值边界与调度次数。保住逐 bit 的算法身份需要图边界，图边界需要调度，而每次调度要约 337 微秒——比它承载的算术贵三个数量级。H1e 剖析诊断（见下）把这个矛盾从"一次失败的对照"升级成一条可陈述的定律：

在提前编译的加速器上，一次图调用有 10²–10³ 微秒量级的固定地板，且与它承载的算术量无关——决定性旁证是两条路径的设备执行总时长在测量精度内完全相同（−0.05%），而调度次数相差 6.7 倍，墙钟却变差 1.28%：代价被干净地隔离在边界穿越本身，不在任何一种"工作"上。

由此得到的推论对整类设计成立：把控制逻辑搬上加速器，其收益上界等于它移除的主机侧关键路径成本；在设备受限的负载上这个上界趋近于零（本例 0.19%），而代价随调度次数线性增长（本例每次跳步 1.099 ms，是所替代主机工作的 6.8 倍）。该方向在算术上就不可能赢，与实现质量无关。

这条定律反过来选中了现役架构：策略留在图外、主机侧查表、跳步完全不触碰设备——不是妥协，而是被调度经济学逼出来的最优解。这也是这批"失败实验"真正挣到的东西：把一个设计选择变成了有测量支撑的定律。
H1e 剖析诊断 · 2026-08-12主机搬运究竟是被掩盖，还是本来就不在关键路径上诊断完成

用已采集的剖析数据重算，答案比"被主干计算掩盖"更锋利：那 330 MiB 去噪期主机流量最多值 6.2 毫秒，占去噪循环的 0.19%——不是省不下来，而是本来就没有东西可省。与此同时，运行时事件显示两条路径的设备执行总时长完全相同，而执行次数相差 6.7 倍：回归 100% 来自边界穿越，0% 来自计算。

诊断目的

H1e 已经给出端到端负结果，但"为什么"有两种解释：① 省下的主机流量被新增调度抵消（两者都在关键路径上，只是后者更贵）；② 省下的主机流量从来就不在关键路径上（前者根本不是成本）。两者对论文的表述强度完全不同——前者是一次工程权衡，后者是一条定律。区分二者不需要任何新的机器时间。

① 无权重的小图继承了大模型的身份（H1a）——控制图数学上不含权重，却因为沿用了主干的配置与路径身份，让共享权重存储错误硬链接了 22.7GB 检查点并在加载时初始化到设备。内容身份必须包含组件角色与权重策略，否则小图会静默继承大模型的生命周期。

② 形状才是路由身份（H1c-a）——两个入口点的输入形状列表相同、只有数据类型不同，而运行时路由表只按形状匹配，后注册的覆盖了先注册的，最终在错误的图上崩溃。多入口的形状签名必须全局唯一，数据类型不足以区分。

③ 一个句柄不等于一个请求（H1d）——请求 A 先 staging、请求 B 后 staging，再用 A 的旧句柄时主干输出直接错成相对 L2 = 1.0。原因是同一个可执行体复用了输出缓冲。活跃请求必须拥有释放前不被复用的独占设备槽位，而槽位是有界资源，必须接入准入控制。

H1 的原始假设、判据与停止条件

实现最小版本：K=2 常驻 anchor，host 每个 skipped step 只下发两个 coefficient。与当前路径做端到端 A/B，测：

  • 每 skipped step latency 与整图 end-to-end latency；
  • host↔device tensor traffic / synchronization 次数；
  • HBM 占用与额外 graph I/O；
  • 数值 parity：与当前 predictor 输出逐元素或范数级一致。

判据：如果 resident predictor 没有减少任何可测的 host/device 或 runtime 开销，而且也不能为后续 TP-aware dataflow 提供结构优势，则主线需要收缩；反之它成为所有后续设计的设备状态底座。

H1 的系统边界（2026-08-12 代码审计后补充） 当前 FLUX 路径由 Python CacheRunner 保存 anchor，并在 host 侧做线性组合；scheduler 与 latent 更新也仍在 host loop。现有 fused probe 只证明“一个独立小图中的参数可以通过 alias 跨 invocation 常驻 HBM”，没有证明 backbone 输出可以零拷贝进入另一个 predictor NEFF。所以只编译一个线性组合小图、但把 512KB tensor 往返搬运，不能算 H1 成功。

H1 实验拆成连续 gate。H1a（standalone spike）验证 K=2 alias state 与数值语义，并直接证明“单独 post-gather predictor NEFF”会产生大 tensor 往返。H1b（graph-boundary feasibility）验证多 entry-point 共享可变 state 和 ranked tensor 跨 NEFF 传递。H1c（backbone integration）把真实 predictor、scheduler、latent 与 FLUX backbone 连成双向 data plane。H1d（request context）解决请求内不变 tensor 的一次性 staging、slot ownership 与隔离。上述 gate 只建立 architecture boundary；只有完整 50-step real-prompt end-to-end A/B 才允许报告 speed/quality frontier。

停止条件：若跨 NEFF handoff 必然把 anchor materialize 到 host，且 predictor + scheduler 无法在共享 resident state 的图边界内组合，则独立 predictor NEFF 会增加而不是减少传输；此时应收缩为“host-controlled multi-graph runtime”或重画图边界，不能继续使用 accelerator-resident 的表述。

先失败一次：一个 staging entry point 不是多请求存储

v1 只有一个 staging entry point。A 第一次进入 backbone、B 第一次进入 backbone都与 direct-host context bit-exact；但 stage B 后再次使用旧 A handle，backbone output 变为 max abs 268.546875、relative L2 1.00088。其它 23 类检查没有同时失败。原因不是 layout 或数值误差，而是同一 executable 再执行时复用了输出缓冲，B 覆盖了 A。由此得到不可省略的 runtime abstraction：Python handle 不等于 request identity；live request 必须拥有独占、release 前不复用的 device slot。

为什么省了 91.7% DMA 仍变慢

对照每 rank 的 denoise 只有 12 个 backbone entry points。resident 为了保持当前 host algorithm 的 BF16 intermediate contract，需要：

  • 12 次 backbone + 12 次 cache_anchor_step；
  • 38 次 cache_predict + 38 次 cache_scheduler_step；
  • 1 次 context stage、1 次 initialize、1 次 finalize。

合计 103 entry points/rank，比 materializing 多 91 次/rank。profile 中 cache_predict 和 cache_scheduler_step 的 median per-rank execute 各约 337μs/332μs；算子很小，但 76 次独立 dispatch 加上 12 次 anchor state update 抵消了 DMA 减少。真实 backbone 本身在两 arm 的调用数相同（12 次），median per-rank execute 也近似相同（267.46ms vs 267.09ms），因此回归不是模型计算变慢。

  • 这里揭示的是 AOT executable contract 缺口。在 eager host 代码里，一个 dtype cast 看起来像算法边界；在 AOT 图里，如果没有 runtime 承诺的 materialization/rounding primitive，同一个 cast 可能只是一条可消去的数据类型路径。系统论文必须把 numerical contract 与 graph boundary 一起定义。

改用循环把连续的跳步打包成一次调用（入口点 103 → 33 的投影）。三条前端路径全部在生成 HLO 之前就失败，从未到达编译器后端，因此没有任何硬件数字。顺带澄清一条内存契约：片上缓冲每步清空，跨步常驻只能在显存。

实验目的

H1f 说明 straight-line fused graph 即使插入 optimization barrier，也不能把中间 BF16 cast 变成可靠的 executable contract。H1g 因此不再尝试阻止 compiler fusion，而是改变控制流：把 HBM-resident BF16 latent 作为 XLA While 的 loop carry，让每轮 body 的输入/输出 dtype signature 强制定义 step boundary；同时把一段连续 skips 放进一次 invocation，从架构上解决 H1e 的小图 dispatch explosion。

Memory-contract 澄清 H1g 的目标从来不应表述为“让 anchors/latent 跨 step 留在 SBUF”。SBUF 是 step-local SRAM scratchpad，每个 diffusion step 必定清空，所以跨 step persistence 最多发生在 HBM。即使 H1g 编译成功，它能争取的也只是：① 一次 host/runtime invocation 执行多轮；② BF16 loop signature 固定数值边界。每轮仍需要 HBM↔计算单元的数据移动，不能声称消除了 step 间 HBM traffic 或实现 SRAM-resident denoising state。

固定 A12 的 38 个 skips 自然形成六段：6–8、10–14、16–20、22–30、32–40、42–48。候选使用长度 9 的静态 packet：[9,2] FP32 coefficients 和 [9,1] FP32 Δσ；不足 9 步的段用 Δσ=0 padding。若能执行，完整 cache schedule 每 rank 只需 1 initialize + 12 anchor + 6 segment + 1 finalize = 20 个 cache entry points；加上 12 次 real backbone 和一次 context stage，完整 resident request 预计从 H1e 的 103 降到 33。

冻结 gate 与实验边界

  • G0 host reference：先验证固定九轮、zero-delta padding 与显式逐步 BF16 predictor/scheduler 完全一致。
  • G1 compile while：必须在 TP4 software stack 中生成包含真实 XLA While 的 HLO，经过 neuronx-cc 编译并 load；不能把九轮静态展开冒充 persistent loop。
  • G2 single-active：同一 segment graph 每次只激活一行，完整 50-step 所有 latent 必须 bit-exact。
  • G3 real segments：用六个真实 multi-active packet 执行 A12，每个 segment endpoint 与 final latent 必须 bit-exact。
  • G4/G5 dispatch 与 boundary：只有 G1–G3 通过，才允许验证 20-entry schedule、零中间 tensor materialization 和 segment latency。

主线 BIn-device predictor 与 TP-aware dataflow核心 co-design

设计目标

对 skipped step，预测仍是小规模线性组合：v̂t = Σ wkva_k。系数是几个 scalar，anchor 是大 tensor。因此最自然的数据流是：host 只下发系数，Trainium 在本地读取常驻 anchor 并完成组合。

TP4 取舍

如果 anchor 保持分片，predictor 也可在各 rank 独立完成 shard-wise 线性组合，直到真正需要完整输出的位置再进入已有 collective。这样 cache step 不必因为 predictor 自身新增跨核通信。若把 anchor 提前 materialize 成完整张量，则实现简单，但会产生 4× replica 和更多 HBM traffic。

论文价值

这里的贡献不是“线性组合很便宜”，而是证明 cache prediction 与 tensor-parallel sharding 可交换，并据此重排 state placement 与 collective boundary。这是明确的 communication–storage–compute tradeoff。

主线 B 的实验计划H2 · 分片放置 vs 完整复制

要回答什么。主线 B 主张预测与张量并行分片可交换——同样的线性组合，放在集合通信之前（各核只处理自己那片）还是之后（每核持有完整张量），数学结果一致。既然数学一致，胜负就完全由硬件常数决定：显存占用、冗余计算、以及是否需要额外的标量通信。

为什么必须实测而不是推算。两种放法各有一个不可通约的代价：保持分片省下四倍显存，但预测结果要在需要完整张量的地方汇合，可能引入一次额外的集合通信；完整复制实现简单、不加通信，但每核多存四倍并做四倍冗余计算。浮点运算次数在这里没有判别力——H1 那条链已经证明，真正决定成败的是调度与通信的固定开销，不是算术量。

为什么它与 H1 的失败无关。这是本条最重要的性质：放置问题在主机侧路径上同样存在。即使常驻方案的速度主张被拒、系统继续用主机侧的 A12，anchor 该以分片还是完整形式保存、预测在通信的哪一侧完成，依然是必须回答的设计问题。所以 H2 与 H1e 的负结果正交，不受它牵连。

意义。这是论文里最核心的"通信—存储—计算"三方权衡，而且它是可以给出定量结论的那一类：同一份数学、两种放置、一张对照表。

H2 · TP-aware placement：pre-gather vs post-gather

分别编译两种实现：① anchor 保持 shard，predictor / telemetry 在 collective 前完成；② gather 后保存完整 anchor。不要用 FLOP 猜赢家，直接测：

  • HBM footprint；
  • 额外 scalar collective 固定延迟；
  • redundant compute；
  • end-to-end step latency；
  • 编译时间、NEFF 大小与 graph stability。

这项实验决定论文中最核心的 communication–storage tradeoff。

主线 CScalar control plane连接 compiler 与 runtime

抽象

编译图负责 tensor data plane：DiT、anchor store、predictor、必要的 reduction。运行时策略保留在图外，只通过少量标量控制图的执行，例如 predictor 系数、step id、anchor mask、剩余 budget。这样 policy 变化不要求重新编译 23GB 图。

Gram tap 的位置

Gram reduction 被降级为一个telemetry primitive：新 anchor 产生时，可选地输出它与 resident anchors 的 partial Gram slice，用于 profiling、runtime auditing 或 adaptive extension。它不是 cache 正确性的前提；没有 Gram tap，静态 offline policy 仍可运行。

为什么仍值得做

Gram 的价值在于它把高维 device state 暴露成可复用的 scalar geometry，而不是“发现了一个新的 AI predictor”。同一个 telemetry 接口可供 brake、debugging、quality receipt 或后续 adaptive policy 使用。

主线 DAOT-aware policy/runtime系统层

设计

把 cache policy 物化成小型、可哈希、可版本化的策略对象，而不是把控制逻辑编进模型图。图的 tensor contract 保持稳定；不同 static schedule、不同 coefficient 表、不同 safety policy 在同一 compiled graph 上运行。

要证明的不是“哈希日志很新”

真正要测的是：策略切换是否零重编译、图输入输出结构是否固定、control-plane latency 是否可以忽略，以及 fail-closed 行为能否在不改 tensor graph 的情况下完成。

主线 C 与 D 的实验计划H3 · 张量图固定，策略可变

要回答什么。主线 C 和 D 共同主张"张量图保持固定，策略在图外自由更换"。这句话如果停留在概念图上没有任何价值；要成为系统贡献，必须证明它是可执行的运行时契约：在同一份编译产物上换掉调度表与系数表，确实不触发重编译，控制面延迟确实可以忽略，失败时确实能 fail-closed。

为什么这样设计。判据刻意选成"至少三套不同的调度与系数组合"，而不是一套——因为一套只能证明"能跑"，三套才能证明"图的输入输出结构确实与策略无关"。同时记录内容哈希身份，是因为 H1a 那次 22.7GB 事故已经证明：身份定义漏掉组件角色与权重策略，小控制图会静默继承大模型的生命周期。所以身份验证不是形式主义，是这条主张的一部分。

意义。这是当前架构里唯一一条已经在生产路径上成立、只差把它测出来的主张——现有系统的策略本来就是图外的一份 JSON。它也是"质量优先求最大加速"能落地的前提：认证换档如果要重编 23GB，整个阶梯式认证就没有实际意义。

H3 · Scalar control plane 与 policy invariance

在同一份编译图上切换至少三套 schedule / coefficient profile，验证不触发重编译；记录每 step control payload、host latency、fail-closed path 和 content-hash identity。目标是证明“tensor graph 固定，policy 可变”不是概念图，而是实际 runtime contract。

主线 EAnchor as a serving resource服务层扩展

一个真实 anchor 对应一次完整 DiT step，也对应约固定的 accelerator service time。因此 serving scheduler 可以把“多给哪个 request 一个 anchor”视为显式资源分配。第一版不要求 online quality predictor：可以先用 offline-derived schedule 和已认证的 budget class 做资源分配；如果 telemetry conditional bound 后续成立，再升级为 request-specific allocation。

主线 E 的实验计划H4 · 把锚点当作可调度资源

要回答什么。主线 E 把"下一个设备时隙给哪个请求"当作显式的资源分配问题。第一版刻意不引入任何在线质量预测器，只用离线已认证的预算类别做分配。

为什么先做这个便宜版本。这是一条下界测试：如果连"用静态预算类别在步粒度共享设备"本身都拿不到服务收益，那么再复杂的在线控制器更不会有——而在线控制器的证据链（见下面的可选扩展）目前恰好也没通过。先花小钱确认地板存不存在，再决定要不要盖楼。

意义，以及它为什么是 H1e 那个负结果唯一可能的翻盘方向。这条线的指标是吞吐、尾延迟与公平性，不是单请求延迟。H1e 测的是孤立单请求，此时主机的内存搬运被 267 毫秒的主干计算完全掩盖，所以省掉它换不来任何延迟。但在并发场景下，那些搬运消耗的是所有请求共享的主机周期——12 倍的流量削减有机会在吞吐上兑现，即使单请求延迟差了 1.3%。这是一个明确、可测的翻盘条件，而不是安慰性的说法。

K 扫描实验 · 2026-08-12仿射折叠与重用阶数解放：恒等式成立，奖品不存在否决

折叠恒等式精确成立——一整段连续跳步可以离线塌成对锚点的一次仿射组合，阶数的运行时代价归零。但它承诺的奖品不存在：把锚点数从 2 加到 8，只买到 2.4%–3.3% 的最终偏差改善；而少放一个真算锚点要付 38%–74%。差一个数量级以上，"高阶换锚点"的兑换不成立。

实验目的

候选的推理链是：主机必须持有并乘 512KB 张量 → 这是"外推固定用 2 个锚点"的真实原因（系统理由而非数学理由）→ 折叠把阶数的运行时代价归零 → 阶数可以纯按质量选 → 若高阶能让动态规划在同等质量下少放一个锚点，一个锚点 = 267 毫秒 = 端到端 7.4%。前三环都是对的；本实验检验最后一环。

无约束 DP 与真机反馈门 · 2026-08-12warmup 与 gap 上限不是丑陋——是反馈知识的手工编码离线 −51% → 真机 +69%，约束保留

删掉全部手选调度约束（warmup=6、gap 上限 6/10、相位边界 21），只留机制强制的最小集（锚点 ⊇ {0,1,2,49}），让带实测成本的精确动态规划自由放置锚点。离线成绩惊人：同为 12 锚点，无约束解的 holdout 偏差比生产表低 51%；10 锚点打平生产的 13 锚点。真机反馈门当场反转：真实偏差 0.4732 对生产表的 0.2796——差 69%，侵蚀比 ×10.82 对 ×3.08。这是目标函数反转（当年发生在权重上）在调度层的重演。

实验目的

丑陋清单里 warmup=6、middle/tail gap 上限、相位边界都是手选常数，无法迁移到别的模型。修法候选之一是直接删除——若带实测成本的 DP 不需要它们，常数就消失了。本实验先离线检验（无约束 DP vs 生产表），发现巨大离线收益后立刻上真机反馈门，判读标准在跑之前写死。

机制：为什么离线赢家在真机必输

无约束解把调度结构整个反转：生产表是"密集 warmup + 稀疏尾部"，它是"稀疏头部 + 密集尾部"（第 2→9 步连跳 6 步）。可加成本模型按 |Δσ_t| 给早期跳步定了低价（早期 Δσ 小），但反馈的定价完全不同：早期注入的偏差要被其后四十余次模型调用连乘放大——这正是权重层那次反转（纯全局离线 −46% → 真机全败）的同一机制，换了个作用对象。生产表的密集 warmup 恰好把早期路径偏差压住，它编码的是可加模型看不见的反馈知识。

含义：丑陋清单要重新分类

  • warmup=6、gap 上限、相位边界：从"手选丑陋"移入"待推导的反馈约束"。删除被真机否决；诚实的修法是给它们一个测量出处——候选方向是把 anchor 可见路径偏差的包络作为 DP 的显式约束（权重层的路径正则化已在真机验证过同一思想），使这些常数由校准测量导出而非手选。这也自动解决可迁移性：规则迁移，常数不迁移。
  • q95 聚合的修法保留：换成契约推导的 q90 与本次反转无关（两种口径的无约束解都翻车），出处修正仍然成立。
  • 反转主题第三次现身：权重（离线终点最优 → 真机崩溃）、深度（分段缓存 → 聚合点最稳）、现在是调度（无约束 DP → 反馈否决）。三个独立对象上同一条教训：teacher-forced 世界里的最优解，其激进部分恰好落在反馈放大最强的地方——这已经不是巧合，是这类系统的结构性性质，值得作为论文的统一论点。

为什么这是一个架构问题而不是实现细节

内积是全收缩，与任意切分轴可交换，所以两种放置数学上完全等价——胜负因此纯粹由硬件常数决定，这正是架构实验该有的形状：

这份估算真正确立的东西，以及它的边界

确立的：抽头在两种放置下都远低于噪声（<0.03%），所以"把内积归约焊进本来就要发生的那次大图调用"这个原语在量级上成立。第二轮三个存活候选（预认证格上的在线重规划、赤字核账降档、空闲通道真值稽核）都以此为地基，这份估算把它们的公共前提提前锁住了。

没有确立、只能靠编译回答的：把算子追加到主干图尾部，会不会扰动编译器对既有集合通信的重叠调度（编译参数里开着 --enable-ccop-compute-overlap）。算术量级说它至多是几十微秒，但调度扰动不是算术，可能放大。因此下一步仍需编译两个带抽头的主干变体做实测对照，但目标已经从"哪种放置更快"改成"抽头是否扰动那 267 毫秒的一步"。

诚实的风险 如果实测确认两种放置都在噪声内（大概率），那么放置之争不构成论文贡献，应写成实现说明；论文里留下的是那条硬件常数结论（在此规模下冗余计算 ≈ 通信）与"零调度抽头原语成立"这个使能性结果。要让它成为独立贡献，需要把规模/并行度扫开，证明交叉点的位置是可预测的——那是更大的一笔投入，应在核账线本身证明有价值之后再考虑。

实测结果：估算错了约 40 倍，抽头不是免费的

编译成功、机制验证通过，但抽头把主干一步从 266.53 ms 拖到 269.66 ms，+3.13 ms（+1.17%）。每请求 12 个锚点步合计 +37.6 ms = 去噪循环的 +1.16%——几乎等于 H1e 整条常驻路径的回归（+41.75 ms）。上面那份编译前估算给出的是 0.01–0.03%，错了约 40 倍。"零调度"不等于"零成本"。

机制验证通过

返回的 Gram 行两个分量相等（402300.375, 402300.375），即 <anchor, c> = <c, c>。因为每次调用输入相同、输出也相同，这个等式恰好证明常驻锚点确实存住了上一次调用的输出并跨调用原地更新——别名写回按契约工作。

估算为什么错了 40 倍

估算用 cache_predict 图的 26 μs（262144 元素的两项线性组合）作同规模归约的代理，只算了算术。实测的 3.13 ms 是它的 120 倍，差额来自算术之外的三件事：

  • fp32 物化与写回：output.float() 生成 1 MB 的 fp32 张量，别名每步再把这 1 MB 写回显存。这是真实的显存流量，而代理里没有。
  • fp32 锚点的读取：内积要读另一份 1 MB。
  • 它落在关键路径的尾巴上，无可重叠——这一条是架构层面的关键。图里其余部分被编译器精心安排成计算与集合通信重叠（--enable-ccop-compute-overlap），而抽头依赖最终输出、被追加在最后一个算子之后，后面已经没有任何东西可以和它重叠，延迟因此完全暴露。

所以这条结论要比"抽头贵"更精确：在一个已经被调度得很满的图的尾部追加工作，其代价不是它的算术，而是它无处隐藏的显存流量。这也解释了为什么代理式估算会系统性乐观——代理是个独立小图，它的 26 μs 里那点流量本来就无处可藏，比例上却小得多。

对三个存活候选的影响

第二轮里预认证格、赤字核账降档、空闲通道真值稽核都以"零调度抽头几乎免费"为地基。这份实测把地基改写成：抽头可行、机制正确，但每锚点步要付约 1.17%。于是它们的收益必须先跨过这道门槛才谈得上净赚——例如核账降档若要靠"简单 prompt 少跑一个真实步"回本，省下的 267 ms 要先抵掉 12 步抽头的 37.6 ms，净收益从 7.4% 降到约 6.2%，仍然为正但不再是白拿。

成本拆解：全部在别名写回，而且与写回大小无关

用两个额外变体做减法，把 3.13 ms 拆开。noalias 与 post 逐字相同（同样的 fp32 锚点、同样两次归约），唯一差别是不写回；bf16 把写回量砍半（1 MB → 512 KB，别名目标用 reshape 造出不同的 HLO 值——reshape 在连续内存上是位重解释，本身不花钱）。

两条都很干净：

  • 归约本身免费。完整读两遍 512 KB 再各归约成一个标量，实测不比基线慢——它藏进了编译器既有的重叠调度里。这一条印证了最初的直觉：内积确实是能焊进大图而不被察觉的运算。
  • 全部代价来自"图带一个别名输出"这件事，且与写回大小无关。把写回从 1 MB 砍到 512 KB 毫无效果（269.66 → 269.94，反向且在噪声内）。所以它不是带宽成本，是跨调用原地写这个契约本身的固定代价——多半来自运行时必须保证写完成才能进入下一次调用而引入的物化/序列化。

结论：这个抽头不该建，Gram 应该在主机上算

既然归约免费而跨调用常驻状态昂贵，就该问：这件事非得在设备上做吗？答案是不必——主机本来就持有全部锚点（主干每个真算步都把输出返回主机），所以主机算 Gram 不需要额外搬运任何数据。实测主机侧算同样两个内积 0.041 ms/步、每请求 0.49 ms、占去噪循环 0.015%，而图内抽头是 37.54 ms、1.154%——主机便宜 77 倍。

这把调度地板定律推进了一步 定律原本说控制逻辑只能活在两处：(a) 主机侧，或 (b) 融进一次本来就要发生的大图调用；(c) 自开小图必亏。本实验给 (b) 加上了一个此前没有的限定：

"融进已有调用"只有在它不需要跨调用常驻状态时才是免费的。一旦需要（也就是需要别名），就要付一笔与数据量无关的固定费用，而这笔费用在本例中比主机方案贵 77 倍。

于是三次实验指向同一件事：在设备受限的负载上，主机几乎总是缓存控制逻辑正确的归宿——H1a–H1g 是因为调度地板，H2′ 是因为别名的固定代价，而两次的另一半原因都是同一个：主机侧的工作本来就近乎免费（占去噪循环 1.52%，其中缓存相关只占 0.19%）。
这对第二轮的三个存活候选意味着什么 预认证格上的在线重规划、赤字核账降档、空闲通道真值稽核，三者都把"图内 Gram 抽头"当作地基。地基要换，但方向不必放弃：它们真正需要的是"每个真算步拿到这一步的 Gram 行"，而这件事在主机上做又便宜又不需要新编译产物、不需要别名契约、不需要重编译 23GB。换成主机侧实现之后，这三条候选的前置成本从 1.154% 降到 0.015%，等于回到了它们最初被提出时假设的那个"几乎免费"的世界——只是免费的地方不是设备，是主机。

同时应当撤回本记录早先那句"零调度抽头原语在量级上成立"的表述：原语确实成立，但它不是免费的，而且它要解决的问题有一个便宜 77 倍的现成解法。

过程中撞到的四条契约，本身就是可复用的系统结论

这个抽头编译了四次才通过，每次失败都暴露一条 AOT 服务栈的隐式契约。它们与 H1a–H1g 的三次事故同类，建议合并进论文的实现章节。

#症状契约
① Trying to set up alias at {3} which is an invalid index for shape (bf16[…], f32[3], bf16[…]) 同时作为普通输出与别名目标的张量会被 XLA 去重，别名索引随之悬空。这正是 H1b 记录过的那条——记录了却仍然踩中，说明它需要变成代码里的断言而不是文档里的段落。

③ RuntimeError: Missing weight tensor with key transformer.proj_out.bias 共享权重存储的键里没有任何图结构判别符——见下方独立记录。
④ 追踪期取 rank 会把 rank 0 的切片烤进所有 rank builder 只追踪一份程序供四个 rank 执行（SPMD），所以任何依赖 rank 的行为必须从设备状态读取（主干用 global_rank.rank），不能用 Python 时的 rank 查询。分片放置因此推迟。
事故复发：共享权重存储缺少图判别符（已修） 第三次编译看似成功，但载入时报缺键。查证发现产物里的权重文件链接数为 5、日期是 8 月 9 日——它是被硬链接过来的基线主干的检查点。

根因：shared_weights.store_key 的输入（scheme、源检查点路径、dtype、并行度、world_size、cp/sp/cfg 开关）全部描述"检查点"，没有一项描述"消费它的图"。于是同一份检查点上两个期望不同 state-dict 命名空间的应用哈希到同一个键，后者静默收到前者的分片。

这比 H1a 那次更危险：H1a 是响亮地失败（凭空出现 22.7GB 权重），这次是静默加载了错误的权重，只因恰好有一个键名对不上才暴露。若两侧命名恰好一致，它会安静地用基线权重算出错误的数字。H1a 记录了"内容身份必须包含组件角色与权重策略"，但没有落到代码里，于是它复发了。

修复（最小且向后兼容）：应用可声明 weight_namespace；声明了才进入键。未声明的应用键值逐字节不变，现有存储条目全部保持有效。抽头应用声明为 flux-gram-tap，随后正确分片了自己的权重并成功载入。

4 H4 服务层时隙分配（并发吞吐）——先做一次现役路径的并发压测作为前置门 原本是 H1e 负结果唯一可能的翻盘方向：孤立单请求下省流量无用，并发下省的是共享的主机周期。但第 1 项诊断给出了一个不利的算术：主机侧在去噪循环里的全部时间只有 49.6 ms，设备侧是 3204 ms，要让主机成为共享瓶颈需要并发把主机负载放大约 65 倍，而单设备在一个请求下已忙到约 98%，达不到该并发度。这是推导不是实测，因此先花十几分钟用现役路径压并发把它证实或证伪，再决定要不要投入调度器工程 若吞吐一路涨到设备饱和都没有出现主机导致的退化，则翻盘条件被否定，常驻这条线以"已验证机制、无性能贡献"定稿，不必再建调度器
一个被冻结协议遮住的选项 目前所有 gate 都要求与主机语义逐 bit 相同。这个要求作为归因工具是正确的——只有算法完全一致，时间差异才能归给架构。但它现在已经变成设计约束，而且正是它挡住了入口点 103 → 65 的那条路。

值得区分的是：逐 bit 相同是方法学要求，部署只关心质量契约。H1c-a 里那个融合变体的偏差是最终潜变量相对 0.26%，而且它少了一次舍入，质量未必更差。用质量契约（逐提示词的伤害上限加二项置信上界）去判它，它就是一个合法的新算法契约。这条不保证翻盘（65 次调度仍比 12 次多 53 次），但它是当前唯一一条不依赖运行时新增原语的路，而且判它只需要跑一次现有的认证流程。
