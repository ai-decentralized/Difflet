FP8 DiT Inference on Trainium

Summary

We quantize the large linear layers of each DiT (attention q/k/v/out and the FFN) to FP8 e4m3, with FP8 weights and FP8 activations, and run the matmuls in FP8 on trn2.3xlarge at tensor parallelism 4. Everything else (embedders, modulation, norms, the final projection, text encoders, VAE) stays bf16.

The scheme we started from is the one FastVideo uses on GPUs: per-tensor weight scales and dynamic per-tensor activation scales computed on every forward pass. On Trainium that scheme made the DiT step 15 % slower than bf16, even though the FP8 matmuls themselves were faster. We ship static activation scales calibrated offline instead, which is both faster and closer to bf16 in output quality.

FP8 GEMM in one page

A GEMM (General Matrix Multiply) is a matrix multiply, C = A × B. Each value of C is one row of A multiplied element by element with one column of B, then summed. A tiny example:

A (2×3)        B (3×2)          C = A × B (2×2)
[1 2 3]        [ 7  8]          [1·7 + 2·9 + 3·11   1·8 + 2·10 + 3·12]   [ 58  64]
[4 5 6]   ×    [ 9 10]    =     [4·7 + 5·9 + 6·11   4·8 + 5·10 + 6·12] = [139 154]
               [11 12]

Every output value here needs 3 multiply-adds, one per shared index. Every linear layer in a DiT is a GEMM: y = x · Wᵀ, where x is the activation (one row per token) and W the weight. For Wan 2.1 at 480×832×9, one to_q multiplies a [4680, 5120] activation by a [5120, 5120] weight. That is 24 million output values, each a sum of 5,120 products, roughly 120 billion multiply-adds. Wan has 400 such layers per step, so the GEMMs dominate the step time.

FP8 GEMM scales both operands into the FP8 range before multiplying and scales the result back afterwards:

scale_x = max(|x|) / 240          # 240 = largest FP8 e4m3 value on Trainium
x_fp8   = cast_fp8(x / scale_x)   # quantize the activation
W_fp8   = cast_fp8(W / scale_w)   # done once, offline
y       = (x_fp8 @ W_fp8) × scale_x × scale_w   # dequantize, then + bias

A worked example with one activation row [0.5, −2.0, 1.0]: max(|x|) = 2.0, so scale_x = 2.0 / 240 ≈ 0.00833 and the row quantizes to [60, −240, 120], all inside FP8's ±240 range. The matrix engine multiplies these small 8-bit values, and multiplying the result by scale_x × scale_w brings it back to the original magnitude.

FP8 roughly doubles the multiply rate of the matrix engine and halves the weight bytes. The cost is the extra work around the matmul: finding max(|x|), the quantize pass and the dequantize pass. Whether FP8 is a net win depends entirely on how cheaply the hardware and software stack can do that extra work.

Dynamic scales compute scale_x from the live activation on every call. Static scales use a constant per layer, calibrated offline by running the real denoising loop once and recording each layer's largest input.

Why the extra FP8 work costs less on a GPU

The key fact: multiplying is cheap, moving data is expensive. Chips have a large, slower off-chip memory (HBM, tens of GB) and a small, fast on-chip memory (GPU registers and shared memory; Trainium's SBUF and PSUM, tens of MB). A GEMM is computed tile by tile: blocks of the inputs are brought on chip, multiplied, and the results written back. Any step that adds an extra round trip through HBM adds real time.

For one Wan linear layer the activation is [4680, 5120] in bf16, about 48 MB.

  • On a GPU, the dequantize costs nothing extra. cuBLASLt and CUTLASS FP8 GEMMs take the two scales as arguments. When an output tile is finished it is still in registers; the GEMM's epilogue multiplies it by scale_x × scale_w, adds the bias and writes bf16. No extra pass over the output.
  • On a GPU, max-and-quantize is a separate but cheap pass. It reads the activation once more and writes the FP8 copy. At about 3.35 TB/s on an H100, moving those ~72 MB takes around 20 µs, while the GEMM itself is 120 billion multiply-adds. The kernels are hand-tuned library code.
  • It is not free on GPUs either. A vLLM issue reports online dynamic FP8 running about 18 % slower than BF16 on an RTX 5090. The balance depends on the hardware and the matrix sizes.
  • On Trainium today, both steps cost a full pass. The dynamic max is a barrier: the whole 48 MB activation must be read before any element can be quantized, it does not fit in the 24 MB SBUF, so it spills to HBM. The dequantize is a separate pass on the scalar and vector engines. The matmul got faster (358 → 322 ms) but the vector engine (+66 ms), scalar engine (+43 ms) and doubled HBM writes ate the gain.

An analogy: on the GPU, a fast prep cook chops the ingredients (quantize) and the chef seasons each dish as it leaves the pan (epilogue). On Trainium today, every ingredient has to be weighed before any chopping starts, the counter is too small so they go back and forth to the storeroom, and each finished dish is carried back to be seasoned separately.

Why doesn't Trainium apply the scale before writing to HBM, like a GPU?

The hardware can. The software stack we use today does not do it. A matmul result on Trainium flows like this:

tensor engine matmul
   → result accumulates in PSUM (on-chip fp32 accumulation buffer)
   → the vector or scalar engine moves it from PSUM to SBUF   ← can multiply by a scale on the way, at no extra cost
   → DMA writes it to HBM

The tensor engine cannot write to HBM directly, so a vector or scalar engine already handles every result on its way out of PSUM, and that instruction can apply a scale, a bias or an activation function in the same step. That is exactly a GPU epilogue. An NKI kernel can request it explicitly.

The reason it does not happen today: our FP8 linear is written in PyTorch, lowered to XLA HLO, and compiled by neuronx-cc. In the HLO the chain after the matmul is dot (fp8) → transpose → convert to f32 → multiply(scale) → convert to bf16. The compiler treats the dequantize as ordinary elementwise work, so it evicts the matmul result first and then traverses it again for the multiply and the converts. The transpose and the two type conversions sitting between the matmul and the multiply are typical reasons a compiler's fusion rule does not fire. On GPUs this never comes up, because the scale is an argument of the library GEMM rather than something a compiler has to discover.

There are two ways to get the GPU behaviour on Trainium. A hand-written NKI kernel controls the PSUM eviction directly; this is in progress (see Next steps). Rewriting the PyTorch so the chain lowers more favourably (merging the multiply with the bias add, removing the transpose) is cheaper to try, but depends on the compiler.

In short: on a GPU the dequantize is fused into the GEMM epilogue by the library, and the max-and-quantize kernel is a short, hand-tuned pass on very fast memory. On Trainium the hardware could do the same, but the compiler emitted the dequantize as its own pass, and the dynamic reduction becomes a barrier that forces spills.

Quantization flows side by side

Same idea in all three: FP8 weights, FP8 activations, FP8 matmul with fp32 accumulation, dequantize to bf16. They differ in when the activation scale is computed and in how much of the per-layer work happens on chip.

Flow 3 is the closest Trainium equivalent of the GPU design in flow 1, and with static or per-token scales it removes even the separate quantize pass that GPUs pay for dynamic scales. Its numbers on Wan 2.1 are in NKI kernel results.

Decisions and why

Every optimization was measured on the device with the same prompt, seed and shape, and kept only if the DiT step improved. Wan 2.1, 480×832×9, 20 steps, tp4.

  • Dropped
    FP8 weight-only mode. Weights stored in FP8, matmuls in bf16. Fast to load but no matmul speedup, and not what FastVideo does. Removed to keep one W8A8 path.
  • No change
    neuronx-cc 2.27. About 1 % on both bf16 and FP8 (568.7 / 648.2 ms vs 573.0 / 656.6 ms on 2.26). Not the lever.
  • Kept
    Lean dynamic law: 656.6 → 607.2 ms. Absmax from max/−min reductions instead of an abs pass, multiply by a reciprocal instead of dividing, no clamp, one combined dequantize multiply. Removed abs / divide / clamp passes the profile pointed at.
  • Reverted
    Quantize a shared input once for q, k and v: 639.3 ms. Looked cheaper, measured 32 ms slower. With one quantize per linear the compiler fuses it into each matmul's operand load; a shared FP8 tensor with three consumers must be written to HBM and read back three times.
  • Kept
    Static calibrated activation scales: 607.2 → 586.9 ms. A per-layer constant (calibrated input max × 1.25 / 240) stored in the FP8 checkpoint. No reductions on the device. Calibration runs the real denoising loop once on CPU (20 min to 2.5 h per model).
  • Kept
    Clamp before the FP8 cast in the static path. Mandatory: on Trainium, casting a value above 240 to FP8 gives NaN rather than saturating. Without the clamp the Wan render collapsed to 8 dB. It is also free (586.4 vs 586.9 ms).
  • Kept
    Static over dynamic as the default, also for quality. Same FP8 weights: static gives 24.9 dB latent SNR and 36.7 dB render PSNR vs bf16, dynamic 13.2 dB and 33.0 dB. Dynamic is correct per forward pass (it matches the CPU reference at cosine ≥ 0.9994 in every probe) but drifts over the 20-step loop. Dynamic stays as the fallback when no calibration file exists.

Trainium-specific difficulties

  1. No library FP8 GEMM with a fused epilogue. On GPUs, cuBLASLt and CUTLASS take the scales as GEMM arguments. On Trainium the graph comes from the compiler, which treats the dequantize as a separate elementwise op. Fusion depends on how the PyTorch code happens to lower to HLO.
  2. Global reductions are barriers. A dynamic per-tensor scale needs the whole activation before any element can be quantized. The activation does not fit in on-chip SBUF (24 MB), so it spills to HBM.
  3. "Cheaper-looking" graph changes can be slower. Sharing one quantize across q/k/v cost 32 ms because it defeated an operand-load fusion. Every change has to be measured on the device.
  4. FP8 cast does not saturate. Values above 240 become NaN, so any static scale needs an explicit clamp.
  5. Shape-specific compiler failures. HunyuanVideo's FP8 text-stream q/k projections produced all-NaN output only at 256 text rows and tp4 (next section). Correct on CPU, correct at tp1, correct at 512 rows.
  6. Long feedback loops. A full-model compile takes 5–70 minutes, and AOT compilation means every graph variant is a new artifact. A tiny-model probe harness (device vs CPU reference, real weights optional, tp1/tp4) was essential to bisect issues in minutes instead of hours.
  7. Host resources matter for measurement. A CPU calibration job running alongside a benchmark inflated warm end-to-end numbers and once got a compile killed for memory. All published numbers were re-measured on an idle host.

Case study: HunyuanVideo at tp4

HunyuanVideo rendered garbage in FP8 (6–9 dB) while FLUX, with the same block layout, worked. The CPU reference was healthy. We bisected on the device with the real weights, real text conditioning and production shape:

The compiled graph mis-executes the FP8 text-stream q/k projection, which feeds a per-head RMSNorm, at exactly 256 text rows under tp4. FLUX's text stream is 512 rows, so it never hit this. The fix keeps those two projections in bf16. They process 256 of about 10,500 tokens, so the cost is negligible. Afterwards the full model matches the CPU at cosine 0.99981 and the step is 0.83× bf16.

NKI kernel results (Wan 2.1, in progress)

The kernel (difflet/backends/trainium/nki_kernels/fp8_linear.py) is numerically correct: on the device both modes match the CPU reference at 64 dB, the same as the XLA path, and inside the real compiled model at tp4 (two real Wan blocks, real text) the output matches the CPU at cosine 0.99998.

A standalone single-layer benchmark showed that the existing XLA FP8 static linear is already as fast as or faster than bf16 for every Wan layer shape in isolation (q/k/v 0.70 vs 0.70 ms, FFN-in 1.37 vs 1.46, attention-out 0.74 vs 0.81, FFN-out 1.25 vs 1.60 ms). The remaining whole-model gap is therefore about graph-level scheduling around the linears, which a kernel has to beat inside the full model.

Next steps

The remaining gap on Wan is the unfused quantize / dequantize around each matmul. The option closest to the GPU design is a hand-written NKI kernel per FP8 linear:

for each output tile:
    load x tile and W_fp8 tile into SBUF
    quantize x in SBUF (static scale, or a per-token scale computed on the tile)
    fp8 matmul on the tensor engine, fp32 accumulation in PSUM
    on the PSUM → SBUF move: × scale, + bias, cast to bf16     # the GPU "epilogue"
    write to HBM
  • Static scales first: a constant scale lets the whole layer run in one pass over the activation.
  • Then per-token dynamic scales: a row of 5,120 values fits in one SBUF tile, so each token's scale can be computed in place without a global barrier. This is also the granularity the Wan report uses on GPUs, and it would remove the calibration step if quality holds.
  • Cheaper experiments alongside: rewrite the PyTorch so the dequantize fuses (merge it with the bias add, avoid the transpose between matmul and multiply), and fold scales algebraically (q/k feed an RMSNorm, which cancels a constant scale; attention is linear in V, so V's scale can merge into the next layer's quantize).

Work in progress on Wan 2.1: an NKI FP8 linear kernel in both variants, measured against the current 586.9 ms static path and the 573.0 ms bf16 baseline.
